# 分析機能の棚卸しと、外部ツールとの差分

カブチャレ（kabu-challenge.com）が提供している分析と、このシステムが今持っている
分析を突き合わせ、**手持ちのデータだけで追加できるもの**と**データを増やさないと
できないもの**に仕分けた文書。

## 0. 出典の限界（先に書く）

**このコンテナからは `kabu-challenge.com` と `blog.kabu-challenge.com` の両方に
到達できない**（egress proxyがブロックする）。したがって先方の機能一覧は、

1. 依頼時にいただいた記述
2. 検索結果に出た公式ブログの要約テキスト

の2つが根拠であり、**画面を見て確認したものではない**。細目（たとえばVaRの手法が
分散共分散法かヒストリカル法か、信頼水準が95%か99%か）は未確認である。実装の
参考にする前に、その部分だけは実物を見て確かめること。

一方、**このシステム側の記述はコードを読んで書いている**ので、ファイル名と行の
根拠がある。差分の非対称性に注意。

---

## 1. 先方が持っているとされる機能

| 分類 | 内容 |
|---|---|
| 対象 | 日本株4,000銘柄超、最長15年（ADVANCE） |
| バックテスト | 価格条件・ファンダ条件でルールを組み、過去の成績を検証 |
| 統計の出し方 | 「95%の確率で利益は◯%〜◯%」という区間推定の形 |
| スクリーニング | ザラ場中のリアルタイム抽出 |
| リスク分析 | ポートフォリオのボラティリティ、銘柄間相関、**VaR**、分散効果 |
| 仮想トレード | 紙上での売買記録 |
| 自動発注 | GMOクリック証券・楽天証券連携（BASIC以上） |
| 品質の主張 | PITデータ、上場廃止銘柄の保持、過適合・ルックアヘッド・生存者バイアスへの言及 |

依頼者の評価に同意する点を1つだけ書いておく。**バックテストは勝ち方を発見する
機械ではなく、仮説が過去にどれだけ再現したかを反証する道具**である。この文書の
仕分けもその前提で行う。

## 2. すでに同等以上のものがある

| 先方の機能 | こちらの実装 | 実体 |
|---|---|---|
| バックテストの期待値 | 初日変動率 × 保有日数の条件付き期待リターン面 | `sql/event_study.sql` `return_surface_smoothed` |
| 「95%の確率で◯%〜◯%」 | 期待値の80%下限（`1.2816 × 標準誤差`）を全セルに併記 | 同上 `conservativeLow` |
| 売買ルールの成績 | 待ち日数→買い→売りの順序を保った実損益、勝率、下側10%点 | `return_trade_observations` / `return_trade_plan` |
| 手数料の考慮 | 片道10bpを期待値から引いた `expected_return_after_cost` | `event_study.sql:835` |
| 過適合への対処 | **ウォークフォワード検証**（3分割、各検証区間より前のデータだけで条件とB/Sを決め、未使用期間で実測） | `return_validation_folds` 〜 `return_validation_results` |
| ルックアヘッドへの対処 | イベントのbetaは反応日**より前**の120営業日でのみ推定。決算は提出日（`filed`）基準 | `symbol_betas` / `fundamentals_metrics.sql` |
| ファンダ条件での分析 | 決算指標の横断表（TTM、増収率、粗利率、在庫日数、capex比、R&D比、FCF） | `/fundamentals` |

**先方に無さそうで、こちらにあるもの**が2つある。

1. **重なりを補正した実効標本。** 20日先のリターンを毎日計算すると窓が重なり、
   独立した観測20件分の情報は無い。こちらは `局所実効標本 / 保有日数` を実効n
   として扱い、**10未満のセルは描かない**。これをやらないと、標本の少ない領域の
   期待値がいちばん派手に見える。
2. **ニュースとの接続。** 反応日を特定し、同業ベンチマークにbetaを掛けた分を
   引いて残差を出す。価格だけのバックテストには無い軸である。

## 3. 手持ちのデータだけで追加できる（新規取得なし）

日足コーパス（`adjClose` / `adjVolume`）と決算指標が既にあるので、**外部への
リクエストを1本も増やさずに**作れる。上から順に、費用対効果が高いと考える順。

### 3-1 / 3-2. 無条件の銘柄特性と相関 — **実装済み（2026-08-07）**

`symbol_risk_profile` と `symbol_correlations` を `event_study.sql` に追加し、
レポートの「銘柄の素の性質と相関」に出した。

| 列 | 中身 |
|---|---|
| `annualised_volatility` | 日次標準偏差 × √252 |
| `annualised_mean_return` | 日次平均 × 252 |
| `return_to_volatility` | 上の比。**シャープレシオとは呼ばない** — このコーパスに無リスク金利が無く、分子が超過収益ではないため。銘柄間の順位付けには使えるが、公表されているシャープと比べてはいけない |
| `return_to_downside` | 下方偏差（下落日だけの二乗平均平方根）で割った版 |
| `max_drawdown` | **その時点までの最高値**からの下落率の最小値。初値からではない |
| `positive_day_rate` / `worst_day` / `best_day` / 日次5%〜95%点 | 分布の形 |

相関は上位20組だけ出す。全組み合わせを印刷しても読まないし、**見るべきは
「分散したつもりが1つの賭けになっている」組**だからである。重複期間が60営業日
未満の組は係数が雑音なので落とす。

### 3-3. VaR — 実装量: 中

分散共分散法なら相関行列の次にすぐ出る。ヒストリカル法も日足があれば可能。
**ただし保有数量が無い**。今のウォッチリストは銘柄の集合であって、株数も取得単価も
持っていない。VaRを出すなら**リストに数量を持たせるかどうかの判断が先**である。
金額が入ると、それは実質的にポートフォリオ管理機能になる。

### 3-4. テクニカル条件によるスクリーニング — **実装済み（2026-08-07）**

`price_state()` が日足コーパスから銘柄ごとの**現在の状態**を1行ずつ出し、
決算指標と同じ `summary.json` に載る。決算画面に「条件で絞り込む」を足し、
**ファンダとテクニカルを同じ表で串刺しに**絞り込めるようにした。

| 指標 | 定義 |
|---|---|
| `volume_ratio_60d` | 直近の出来高 ÷ **直前**60営業日の中央値 |
| `rsi_14` | **Cutler版**（単純平均）。Wilderの平滑化とは数ポイント違うので、名前を明示する |
| `sma_50_gap` / `sma_200_gap` | 株価 ÷ 移動平均 − 1 |
| `drawdown_from_52w_high` / `gain_from_52w_low` | 52週高値・安値からの位置 |
| `return_1m` / `return_3m` / `return_12m` | 21・63・252営業日前からのリターン |

3つの判断を実装に埋めた。

1. **出来高比の基準に当日を入れない。** ある日が急増かどうかは**その前の日々に
   対して**決まる。当日を基準に含めると、測ろうとしているものを自分で薄める
2. **履歴が足りない指標は空欄にする。** 60営業日で計算した200日移動平均は
   「遅い平均」ではなく**名前を偽った速い平均**であり、存在しない理由で銘柄を
   スクリーニングの上位に押し上げる。50日は50本、200日は200本、52週は252本を要求する
3. **欠測は条件を満たさない扱いで落とす。** 厳密には「判定できない」だが、
   スクリーニングとしては**表に出た銘柄が実際に条件を満たしている**方が安全である

テクニカル列にはADRガードを掛けない。株価を株価自身と比べているだけなので、
**預託比率は約分されて消える**。株価指標（PER等）で伏せた列が、ここでは読める。

依頼文にあった3つの仮説は、どれもこの層で表現できる。

- 「決算後の下落率とその後20営業日のリターン」→ **実装済み（2026-08-07、下記3-6）**
- 「出来高急増＋PER低位＋利益成長」→ **実装済み**。出来高比・PER・増収率を
  同じ絞り込みで指定できる
- 「52週高値から一定率下落した半導体株の反発率」→ 絞り込みで母集団を作れる。
  「その後の反発率」は既存の条件付き集計側で見る

### 3-6. 決算をイベント源に加える — **実装済み（2026-08-07）**

`fundamentals/symbol=*/part.parquet` から**期ごとに1件**のイベントを生成し、
既存のイベントスタディにそのまま流す。`event_type = 'earnings'` なので、
「イベント種別別」の集計に決算の行が独立して出る。0/1/2/5/20営業日の
リターン、同業beta補正後の残差、過去分位——ニュースイベントと同じ道具が
全部そのまま効く。

**日付は「その期の売上を最初に載せた提出書類」の提出日**を採る
（`min(filed)`）。企業は四半期を8-Kで発表し、数週間後に10-Qで繰り返す。
**市場が動いたのは最初の方**なので、10-Qの日付を使うと
「みんなが既に知った後のドリフト」を測ることになる。

3つの注意を実装とコメントに書いた。

1. **提出書類に時刻が無い。** 多くは引け後に出るので反応は翌営業日になりがちで、
   **0日目の数値は信頼できない**。1日目以降が正直な読み。時刻を推測して
   埋めるより、そう書く方を選んだ
2. **期末より前に提出された行は捨てる。** 終わっていない期を報告できるのは
   タグ付けの誤りだけである
3. **カバレッジの6つのカウンタには混ぜない。** あれはNotionの取り込みの話で、
   決算を足すと**何もクロールしていない日にクロールが改善したように見える**。
   決算は別の2カウンタで数える

### 3-7. 株価との接続（PER・PBR・PSR・FCF利回り） — **実装済み（2026-08-07）**

日足コーパスの直近終値と、XBRLの発行済株式数から時価総額を出し、決算指標の表に
4つの倍率を並べた。**追加の取得は無い。**

**ADRの扱いがこの実装の核心である。** 外国民間発行体（20-F・40-F・6-Kで提出する
会社）は、米国上場されているのがADRで、**これが原株何株にあたるかをこのコーパスは
持っていない**（TSMは1 ADR＝原株5株）。ADRの株価に原株の発行済株式数を掛けると
時価総額がその倍率だけ狂い、**PERが実際より低く出て「割安」に見える**。
誤りとしては最悪の出方——読んだ人が間違った方向に動く——なので、
**これらの銘柄では株価指標を一切出さない**。提出書類の様式から判定できるので、
銘柄名を並べたリストは持たない。

同じ理由で、米ドル以外で計上している会社にも出さない（株価はドル建てである）。
空欄には理由を持たせ、銘柄を開いたときに「ADRの原株比率が不明」のように表示する。
空欄が事実になる。

赤字の期はPERを空欄にする。**負の倍率は割安ではないし、誰もそう読まない。**
PSRは残す。売上は赤字でも正なので、損失を通り抜けて読める倍率である。

**EV/EBITDAは実装しない。** 有利子負債と減価償却費をこのコーパスが概念として
持っていないためで、総負債で代用すると企業価値を大きく過大評価する。
仕様書§2に挙げてあるが、データが足りないことをここに書いて未実装のままにする。

### 3-5. 仮想トレード — 実装量: 中

`return_trade_plan` が既に「何日待って買い、何日後に売る」を出しているので、
**その通りに執行した記録を残す器**を足すだけで成立する。値は日足終値ベース。

## 4. データを増やさないとできない

| 項目 | 何が足りないか |
|---|---|
| **日本株の株価** | **1本も無い。** 決算（EDINET）だけ取り込んでいて、株価は明示的に後回しにした。日本株のバックテスト・スクリーニングはすべてここで止まる |
| 4,000銘柄 | 現在の対象は米国49＋日本17。日足の取り込みは1回20銘柄の上限で段階的に増やす設計 |
| 15年の履歴 | Tiingoは長期日足を返すが、こちらのコーパスは取り込み開始からの分しかない |
| 上場廃止銘柄 | **持っていない。** ユニバースは現存銘柄のCSVなので、こちらには生存者バイアスがある（下記5） |
| リアルタイムのスクリーニング | 分足は保有銘柄のみ。全銘柄のザラ場スキャンはデータ量が別次元 |
| 自動発注 | 対象外。依頼文の懸念に同意する。分析と発注はリスクの次元が違う |

## 5. こちらに残っているバイアス（先方が対処を主張している項目）

先方の主張を検証はできないが、**こちらの現状は正直に書ける**。

**生存者バイアス: ある。** `data/universe.csv` は現存する銘柄の静的な一覧で、
途中で消えた会社は最初から入っていない。「半導体株の反発率」のような集計は、
**反発できずに消えた会社を除いた集計**になっている。

**ルックアヘッド: 部分的に対処済み。** イベントのbetaは反応日より前だけで推定し、
ウォークフォワード検証は各検証区間より前のデータだけで条件を決める。決算指標は
提出日基準なので、発表前の数字を使うことはない。

**ただし、画面の主役である期待リターン面そのものは全期間で当てはめている。**
同じ画面のウォークフォワード欄が「その条件を過去のデータだけで決めていたら、
その後どうだったか」を示す部分で、**信じるべきはそちら**である。面の方は
仮説の探索用と割り切るのが正しい。

**過適合: 検証の枠はあるが、探索回数を数えていない。** 19の変動帯 × 20の保有日数
から最良を選べば、偶然の勝ちを拾う。ウォークフォワードはそれを事後に暴くが、
**多重比較の補正そのものは入っていない**。
