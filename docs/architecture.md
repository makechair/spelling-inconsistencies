# アーキテクチャ

仕様書8〜11章の構成を、実装した形で記述する。仕様書が未定義だった箇所の決定は
[spec-review.md](spec-review.md) の項番で参照する。

## 1. プロセス構成

| プロセス | 役割 | DBへの書き込み |
|---|---|---|
| `collector` | WebSocket常時接続、1分足生成、欠損補完、状態公開 | `bars_1m`, `ticks`, `api_usage`, `collector_state`, `live.db` |
| `api` | 履歴API、SSE配信、静的フロント配信、ヘルスチェック | `symbols` のみ |
| `cloudflared` | 外向きTunnel | なし |

仕様書11.1は collector を「単一Writer」と定義するが、仕様書3.1のウォッチリスト
登録は api からの書き込みである。**単一Writer原則は時系列テーブルに限定**して
再定義した（A-3）。`symbols` は小さく更新頻度も低いため、WALと `busy_timeout`
で十分に安全である。

### なぜ live.db を分けるのか

仕様書はプロセス分離を要求しながら、api が現在値を知る経路を定義していない。
ブローカーやRedisを足さずに済ませるため、**collector が書き api が読む小さな
SQLiteファイル**を使う。

durable な `market.db` と分ける理由は2つある。

1. ティックごとのスナップショット更新が、1分足のupsertが必要とする書き込み
   ロックと競合しない。
2. `live.db` は失っても次の約定で再構築されるだけなので、tmpfs (`/dev/shm`)
   に置いてSSDの書き込み寿命を消費しない。

## 3. 1分足の生成規則

| 項目 | 決定 | 根拠 |
|---|---|---|
| 時刻 | 区間**開始**時刻、UTC | B-2 |
| 入力 | 約定（trade）のみ | B-3 |
| 気配 | 表示用に保持、OHLCVには混ぜない | B-3 |
| VWAP | Σ(価格×数量)/Σ数量 | 仕様書10.1 |
| 確定契機 | 次の分の約定を受信、または経過1秒ごとのロール判定 | 薄商い銘柄の足が永久に開いたままになるのを防ぐ |
| 遅延到着 | 猶予時間内なら過去足へマージ、超過分は計数して破棄 | 古い足を黙って書き換えない |
| 約定なしの分 | **足を作らない** | 仕様書3.3「人工的に値を変化させない」 |

## 4. upsert優先規則（B-5）

`(symbol, timestamp_utc, source)` を主キーとし、SQL側で次を強制する。

```sql
WHERE excluded.is_final = 1 OR bars_1m.is_final = 0
```

| 既存 | 新規 | 結果 |
|---|---|---|
| 確定 | 進行中 | **拒否**（再起動直後の不完全な足が確定足を壊さない） |
| 確定 | 確定 | 採用（訂正、またはREST履歴の権威値） |
| 進行中 | 確定 | 採用 |
| 進行中 | 進行中 | 採用（新しいスナップショット） |

異なる `source` 同士は主キーが違うため上書きされず、別行として共存する
（仕様書5.2）。

## 5. 提供元の解決（B-1）

同一分に複数提供元の行が存在しうるため、読み出し時に優先順位で1本を選ぶ。

```sql
ROW_NUMBER() OVER (
    PARTITION BY timestamp_utc
    ORDER BY <優先順位>, is_final DESC, received_at DESC
)
```

優先順位は `USSTOCKS_SOURCE_PRIORITY` で設定する。API応答は足ごとに採用した
`source` を含み、フロントは期間内に提供元が混在した場合それを明示する。
`?source=alpaca` で単一提供元だけを検証することもできる。

## 6. レート・帯域の管理（A-1, A-2）

- **RESTトークンバケット**: 時間枠と日枠の消費量を `api_usage` テーブルに永続化する。
  プロセス再起動で消費量がリセットされないことが要点である（クラッシュループが
  枠を焼き切る事故を防ぐ）。
- **補完の合体**: 同一銘柄の要求は最も広い範囲へマージされ、1回のRESTで済む。
- **無駄な補完の抑制**: 短すぎるギャップ、および市場が閉まっていた区間の
  ギャップは要求そのものを発行しない。
- **帯域メーター**: Adapterが受信バイト数を累計し、Collectorが差分を月次窓へ
  記録する。閾値超過でログと画面に警告を出す。

## 7. 認証（A-4）

```
Browser ──> Cloudflare Access（Google認証、メール許可リスト）
              │  Cf-Access-Jwt-Assertion を付与
              v
          Cloudflare Tunnel
              v
          api: ミドルウェアでJWTを検証
                - JWKS署名検証（RS256）
                - aud = Accessアプリの AUD タグ
                - iss = チームドメイン
                - exp / iat
                - email が許可リストに存在するか
```

Cloudflare側の設定ミスだけでは公開されない。JWKSが取得できない場合は
**503を返して通す（bypass）ことはしない**。

`/api/livez` だけが無認証で、プロセスが応答するという事実以外を返さない。

## 8. SSEの設計（B-6）

- 変化した銘柄だけを `update` イベントで送る。無変化なら何も送らない。
- 15秒ごとに `heartbeat`（価格を含まない）で接続を維持する。
- `Cache-Control: no-cache`, `X-Accel-Buffering: no` で中間バッファリングを抑止する。
- ストリームには寿命があり、満了時に `cycle` イベントを送って閉じる。EventSource
  が自動再接続するため利用者には見えず、切断を検知できなかったクライアントが
  リソースを保持し続けることを防ぐ。
- ブラウザは切断時に `/api/ping` を叩き、401ならAccessセッション切れと判断して
  リロードし、再認証へ誘導する。

## 9. データベーススキーマ

| テーブル | 内容 |
|---|---|
| `bars_1m` | 1分足。主キー `(symbol, timestamp_utc, source)`、WITHOUT ROWID |
| `symbols` | 銘柄、ウォッチ／保有フラグ、提供元サポート状況 |
| `ticks` | 秒単位スナップショット（既定では未使用、10.2の案1） |
| `api_usage` | REST呼び出し数と受信バイト数の窓別集計 |
| `collector_state` | 銘柄×提供元ごとの最終保存足・最終補完時刻 |
| `market_calendar_overrides` | 算出できない臨時休場・臨時半日立会 |
| `schema_migrations` | 適用済みマイグレーション |

`live.db`（別ファイル）には `live_state` と `collector_status` を置く。

## 10. 米国市場カレンダー（B-4）

固定祝日の土日振替、移動祝日、グッドフライデー（復活祭の計算）、半日立会を
**算出**する。テーブルを持たないので将来の年でも失効しない。国民追悼日など
予測できない休場は `market_calendar_overrides` で補う。

セッション区分（ET）:

| 区分 | 通常日 | 半日立会日 |
|---|---|---|
| pre | 04:00–09:30 | 04:00–09:30 |
| regular | 09:30–16:00 | 09:30–**13:00** |
| post | 16:00–20:00 | **13:00–17:00** |

## 11. 提供元の切り替え

`MarketDataAdapter` は `fetch_bars` / `search_symbols` / `stream` の3つだけを
公開し、提供元固有の形式をすべて内部モデルへ変換する。切り替えは
`USSTOCKS_PRIMARY_SOURCE` の変更で足りる。

切り替えても既存データは上書きされない。異なる `source` の行として蓄積され、
チャートには優先順位に従って表示され、混在期間は画面に明示される（仕様書5.2）。
