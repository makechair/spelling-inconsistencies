# 仕様書妥当性レビュー

**対象文書:** 個人向けリアルタイム米国株チャートシステム 要件・方式比較・推奨アーキテクチャ検討書（2026年7月28日）
**レビュー日:** 2026年7月28日
**レビュー範囲:** 技術的整合性、要件間の矛盾、見積もりの検算、実装時に決定が必要な未定義事項

## 0. レビューの前提と限界

- 本レビューは**仕様書に記載された数値・制約を所与**として扱い、Tiingo / Alpaca / AWS / Cloudflare の一次ドキュメントを再取得しての裏取りは行っていない（本レビュー環境から当該サイトへの外向き接続が制限されているため）。
- したがって「提供元の仕様そのものが仕様書の記載どおりか」は検証対象外である。一次情報での確認が必要な項目には **★** を付す。これらはフェーズ1（動作確認）の実測項目として実装側にも組み込んである。
- 検算・整合性・設計の穴の指摘は、外部情報に依存せず成立する範囲で行っている。

## 1. 総合判定

**骨格は妥当。そのまま実装してよい。** ただし前提の再検証が必要な論点が4件、設計判断が未定義の穴が9件ある。

| 観点 | 判定 | 補足 |
|---|---|---|
| 課題設定（個人1名・常時収集・月10ドル・外出先アクセス） | 妥当 | 要件がスコープと矛盾していない |
| 技術選定（Tiingo / Lightsail / FastAPI / SQLite WAL / SSE / Cloudflare） | 妥当 | 各比較表の結論は要件から正しく導けている |
| 見積もり（容量・コスト） | 妥当 | 第3章で検算した。仕様書の725万行は正確 |
| 前提の検証状況 | **不十分** | 特に Tiingo 無料枠の帯域・REST回数が未検算（第2章 A-1〜A-2） |
| 設計の網羅性 | **不十分** | データモデルと運用の細部が未定義（第4章） |
| 内部整合性 | **一部矛盾** | 単一Writer原則とウォッチリスト書き込み（A-3） |

「この構成は、常時データ蓄積、個人利用、月額コスト、外出先からの利便性、運用負荷のバランスが最もよい」という最終決定（14章）の結論自体は支持する。以下の指摘は**構成の否定ではなく、構成を実際に動かすために埋める必要のある穴**である。

## 2. 前提の再検証が必要な論点（実装をブロックしうる）

### A-1. Tiingo 無料枠 1GB/月 の帯域が、30銘柄の常時WebSocket購読で破綻する可能性が高い ★

仕様書は5章の比較表に「1GB/月」と自ら記載しながら、この枠を**4.3節の「最大30銘柄」と突き合わせていない**。突き合わせると次のようになる。

前提を置いて概算する（1メッセージ150〜200バイト、WSフレーミング込み）：

| 1銘柄あたりの1日の更新件数 | 30銘柄の1日転送量 | 20営業日の月間転送量 |
|---:|---:|---:|
| 1万件 | 約 45〜60 MB | 約 0.9〜1.2 GB |
| 3万件 | 約 135〜180 MB | 約 2.7〜3.6 GB |
| 10万件 | 約 450〜600 MB | 約 9〜12 GB |

**最も楽観的な仮定でも 1GB/月 をちょうど使い切る。**現実的な流動性の銘柄を30本購読すれば数倍から10倍超過する。気配（quote）まで購読すると桁がもう一つ上がる。

これは仕様書中で最も影響の大きい見落としである。以下は本レビューの結論というより、実装側で講じた対策である。

- WSトラフィックが1GB枠に算入されるか自体を一次情報で確認する ★。算入される前提で設計した。
- 購読は**約定（trade）のみ**とし、気配更新を既定で購読しない（B-3とも関連）。Tiingo WSの購読閾値パラメータで制御する。
- Collector に**受信バイト数の実測メーター**を実装し、日次・月次の累計をヘルスチェックへ出す（`/api/health` の `bandwidth` セクション）。フェーズ1の2〜3銘柄で実測し、30銘柄へ線形外挿して枠内に収まるかを判断できるようにした。
- 月次予算に対する警告閾値（既定80%）を設定し、超過見込み時にログと画面へ警告を出す。

**判断:** 実測の結果、無料枠に収まらない場合は「銘柄数を絞る」「有料枠へ移行する」「予備のAlpaca IEXを主系にする」のいずれかの意思決定が必要になる。これは仕様書のフェーズ1に**明示的な判定基準として追加すべき**である。

### A-2. REST 50回/時 の制約と、3.3節「再接続後にRESTで欠損補完」が定量的に衝突する

30銘柄の欠損補完は素朴に実装すると1回あたり30リクエストである。50回/時の枠では**1時間に1回しか全銘柄補完ができない**。3.3節はWS切断のたびに補完すると読めるため、朝の不安定な時間帯に数回切断されただけで枠が枯渇し、以降の補完も日足履歴取得も止まる。1,000回/日の枠も、再接続が多い日には到達しうる。

仕様書はレート制限を「制約」として表に書いているが、**設計要件として扱っていない**。

実装側の対策：

- **永続トークンバケット**（時間枠・日次枠の二段）を DB に持たせ、プロセス再起動をまたいで消費量を保つ（`api_usage` テーブル）。枠を超える要求は待機させ、捨てない。
- 補完要求を**優先度付きキューで合体（coalesce）**する。同一銘柄の重複要求は最新の1件にまとめ、短時間の切断（数秒）ではそもそも補完を発行しない（猶予時間を設ける）。
- 補完対象は「最終保存足の時刻から現在まで」に**欠損が実在する銘柄のみ**に絞る。切断中に市場が閉まっていた場合は補完しない（市場カレンダーで判定）。
- 予算の残量をヘルスチェックへ露出する。

### A-3. 「SQLiteの単一Writer」と「ウォッチリストの登録・解除」が内部矛盾している

11.1節は `collector` を「SQLiteへ書き込む単一Writer」、`api` を「読み取り専用」と定義している。一方 3.1節は「検索した銘柄を保有銘柄またはウォッチリストへ登録・解除できること」を要求しており、この操作は api プロセスからの**書き込み**である。仕様書はこの矛盾を解消していない。

実装側の解決（採用した方式）：

- **単一Writer原則の適用範囲を「時系列テーブル（`bars_1m`）」に限定**して再定義した。時系列への書き込みは collector のみが行う。
- `symbols` / `watchlist` など小さな構成テーブルへの書き込みは api も行う。WALモードでは書き込みは直列化されるため、`busy_timeout` を設定し**短いトランザクション**に限定すれば安全である。競合頻度は「本人1名が時々銘柄を登録する」程度で無視できる。
- api が購読対象を変更しても collector へ通知する経路が無い問題は、collector が `symbols` テーブルを**周期ポーリング（既定5秒）して購読差分を適用**する方式で解決した。プロセス間にキューやソケットを追加しない。

### A-4. 認証が Cloudflare Access の設定のみに依存しており、アプリ層の防御が無い

3.5節は「認証前にはHTML、API、SSEを含めてアプリケーションへアクセスできないこと」を要求し、12章のリスク表も「Cloudflare設定ミス → 意図しない公開」を挙げている。しかし対策は「Tunnel以外の公開ポート閉鎖、Accessデフォルト拒否」だけで、**すべてCloudflare側の設定に閉じている**。設定ミス・ポリシー削除・Tunnelの経路追加ミスがそのまま無認証公開になる。

Cloudflare Access は認証済みリクエストに `Cf-Access-Jwt-Assertion` ヘッダで署名済みJWTを付与する。**アプリ側でこれを検証すれば二重の防御になる**にもかかわらず、仕様書は言及していない。

実装側の対策：

- FastAPI にミドルウェアを入れ、全ルート（静的HTML・API・SSEを含む）で Access JWT を検証する。チーム固有の JWKS で署名検証し、`aud`（Access アプリの AUD タグ）と `email` クレームの許可リスト一致を確認する。
- JWKS はキャッシュし、失敗時のみ再取得する。
- ローカル開発用に `AUTH_MODE=disabled` を用意するが、**待受アドレスがループバック以外の場合は起動時に拒否**し、誤って公開状態で無効化できないようにした。

これにより「Cloudflare の設定ミス」単独では公開されない。

## 3. 検算：妥当と確認できた記述

### C-1. 容量見積もり（10.3節「約725万行」）は正確

仕様書の数字を検算した。プレ4:00〜アフター20:00 ET を通しで960分/日として：

```
960 分/日 × 252 営業日 × 30 銘柄 = 7,257,600 行 ≈ 725万行
```

**仕様書の記述と一致する。**

行サイズは机上見積もりではなく、本リポジトリの実装で実測した（38,402行を投入し `VACUUM` 後のファイルサイズを計測）。

```
実測 176 バイト/行（主キーインデックス込み、WITHOUT ROWID）
  → 7,257,600 行/年 × 176 B = 約 1.28 GB/年
  → 3年で約 3.8 GB
```

**「数GB程度」「40GB SSDで数年間」という仕様書の結論は妥当である。**

なお176バイトは、時刻をISO-8601文字列（25文字）で保存し、それを主キーに含めていることが主因である。エポック秒のINTEGERにすれば概ね半減するが、初期段階では可読性とSQLでの範囲検索の簡潔さを優先した。容量が問題になった時点での最適化余地として記録しておく。

ただし補足すべき点が2つある。

- 40GBのうち OS・Docker イメージ・ログ・**バックアップ一時ファイル**が数GB〜10GB程度を占める。特に `VACUUM INTO` は**DBとほぼ同サイズの複製を一時的に作る**ため、実効的な空き容量はDBサイズの2倍以上を常に確保する必要がある。10.4節はこの点に触れていない。
- 実際には全銘柄が全セッションで約定するわけではないため、上記は上限側の見積もりである。安全側なので問題はない。

### C-2. コスト見積もりは桁として妥当

Lightsail の月額固定（仕様書記載7米ドル）＋ドメイン更新費の月割り＋S3。S3側を検算すると、DB 1GB を gzip で概ね250MB、日次30世代で7.5GB程度、標準ストレージなら月0.2米ドル未満。**月10米ドル以内という目標は達成可能**である。転送量も Lightsail の同梱枠に対して桁違いに小さい。

なお具体的な適用単価（1GBプランが7米ドルか等）は改定されうるため申込時に要確認 ★。ただし**結論（月10ドル以内）を覆す規模の差にはならない**。

### C-3. Cloud Run を採用しない判断は正しい

「最大60分で再接続」「ローカル永続化不可」という理由付けは、常時WebSocket接続とSQLite永続化という要件に対して正しい。インスタンスの生存が保証されない実行環境で「画面アクセスの有無に依存しないデータ受信」（4.3節）は満たせない。

### C-4. S3静的ホスティングを採用しない理由（7.1節）は正しい

S3ウェブサイトエンドポイントがHTTPS非対応であること、本人限定アクセスに追加部品が要ること、同一オリジンにすればCORSとCookie設計が消えることは、いずれも正確である。**特にSSEを使う構成では同一オリジンの利点が大きい**（EventSource のクロスオリジン利用は認証Cookieの送出条件が煩雑になる）。仕様書はSSEとの関連まで書いていないが、結論は補強される方向である。

### C-5. 複数APIを交互に呼んで無料枠を水増ししない方針（5.2節）は正しい

提供元ごとにOHLCの定義（対象取引所、条件付き約定の扱い、出来高の集計範囲）が異なるため、同一系列に混在させると段差が出る。「`source`列に提供元を記録し、復旧後も無条件に上書きしない」という方針は正しい。ただしこれは B-1 の未定義事項を生む（後述）。

### C-6. Route 53 Hosted Zone / ACM が不要という判断（7.3節）は正しい

TLS終端がCloudflare側にあり、AWS側でTLSを終端するサービス（CloudFront / ALB / API Gateway）を使わない構成のため、ACMは不要である。ドメインをRoute 53 Domainsで登録しつつ権威DNSをCloudflareへ委任する構成も問題ない。

### C-7. 「1秒更新」の定義（3.3節）は適切

「1秒ごとに新しい約定が必ず存在するという意味ではなく、受信した最新値を画面へ反映する最大描画間隔」という定義と、「価格に変化がない場合、見かけ上の値を人工的に変化させないこと」という要件は、**個人の分析用途として正しい設計判断**である。多くの実装が陥る「無変化時にダミー値で足を伸ばす」挙動を明示的に禁じている点を評価する。

## 4. 設計判断が未定義の事項（実装前に決める必要がある）

以下は「間違い」ではなく「決めていない」項目である。決めないまま実装するとデータが壊れる。各項目に対して**本実装が採用した決定**を併記する。

### B-1. 一意キーに `source` を含めた結果、表示時の解決規則が無い

10.1節は一意キーを `(symbol, timestamp_utc, source)` とする。これは提供元切替時のデータ保全としては正しいが、**同一時刻に Tiingo 由来と Alpaca 由来の2行が並存しうる**ことを意味する。3.2節は「1分足を表示する」としか書いておらず、**どちらを描画するかの規則が無い**。

**採用した決定:** 設定で提供元の優先順位（既定 `["tiingo", "alpaca"]`）を持ち、読み出し時に時刻ごとに最優先の1行を選ぶ。API応答には実際に採用した `source` を足ごとに含め、フロントは提供元が切り替わった区間を視覚的に区別する。3.2節の「データ提供元を表示」要件を、足単位まで踏み込んで満たす。

### B-2. 足の `timestamp_utc` が区間の開始か終了か未定義

仕様書は `timestamp_utc` としか書いていない。提供元によって規約が異なり、混同すると**1分ずれたチャート**になる。

**採用した決定:** **区間開始時刻**（09:30:00 の足は 09:30:00.000〜09:30:59.999 の約定を含む）。Adapter は提供元の規約を内部モデルへ変換する責務を負う。スキーマにコメントとして明記した。

### B-3. 約定（trade）と気配（quote）のどちらから足を作るか未定義

3.3節は「参照価格更新を受信し、現在進行中の1分足を生成する」とだけ書く。気配更新から足を作ると**出来高が常にゼロになり、始値・終値が約定価格でなくなる**。これは4.3節の性能要件ではなく、データの正しさの問題である。

**採用した決定:** OHLCV の生成には**約定イベントのみ**を使う。気配は「最良気配の表示」用に別扱いとし、足には混ぜない。A-1の帯域問題への対策としても有効である。

### B-4. セッション区分（3.2/10.1節の `session`）の判定根拠が未定義

「通常取引、プレマーケット、アフターマーケットを識別」と要求しているが、判定に必要な**休場日・半日立会（13:00 ET早期終了）**への言及が無い。休場日を考慮しないと、感謝祭翌日の午後に存在しないはずの「通常取引」の足を作る。

**採用した決定:** 米国東部時間ベースの市場カレンダーを実装した。固定祝日の土日振替規則、移動祝日（第n月曜等）、グッドフライデー（復活祭の計算による）、半日立会（独立記念日前日・感謝祭翌日・クリスマスイブ）を算出する。国民追悼日など不定期の臨時休場は算出できないため、**DB側に上書きテーブル**を用意した。

### B-5. `is_final` の上書き保護規則が無い

10.1節は `is_final` 列を定義し「訂正をupsertできるように」とだけ書く。しかし進行中の足（`is_final=0`）と確定足（`is_final=1`）の**優先関係が定義されていない**。素朴なupsertでは、再起動直後に生成した不完全な進行中足が、既に確定していた足を破壊しうる。

**採用した決定:** upsert に次の規則を課した。

1. 同一 `source` 内で、`is_final=0` は `is_final=1` を**上書きしない**。
2. REST履歴由来の確定足は、ライブ集計由来の確定足を**上書きしてよい**（提供元自身の確定値が権威）。
3. 異なる `source` 間の上書きは行わない（別行として保持し、B-1の優先順位で読み分ける）。
4. `received_at` は常に最新の受信時刻へ更新する。

### B-6. SSE の実運用上の注意（バッファリングとAccessセッション切れ）が未考慮

- リバースプロキシ／CDN経由のSSEは**バッファリングで数十秒遅延**することがある。1秒更新要件と直接衝突する。
- Cloudflare Access のセッションには有効期限があり、**期限切れ時にSSE接続がリダイレクト応答になる**。`EventSource` は再接続を試み続けるが、認証画面のHTMLをイベントストリームとして受け取り続けるため、ユーザーには「更新が止まった画面」に見える。

**採用した決定:** レスポンスに `Cache-Control: no-cache`、`X-Accel-Buffering: no` を付け、**15秒ごとのハートビートイベント**を送出する（無変化でも接続を維持でき、かつ価格を人工的に動かさない）。フロントは接続断を検知したら軽量なヘルスエンドポイントを叩き、認証切れ（401/リダイレクト）ならページを再読み込みして再認証へ誘導する。

### B-7. 1GBインスタンス上でのフロントエンドビルドがOOMを起こす

9章は Frontend を「TypeScriptまたはJavaScript」とし、12章は「1GBメモリ不足 → OOM」をリスクに挙げているが、両者が結び付いていない。**バンドラのビルドは実行時より遥かにメモリを食う**ため、1GB機上で `npm run build` を走らせると収集プロセスごとOOMで落ちうる。

**採用した決定:** フロントを**ビルド不要の素の ES モジュール**で構成し、Lightweight Charts の standalone バンドルをリポジトリに同梱（vendoring）した。本番機でのビルド工程とNode.jsランタイムが不要になり、CDN依存も無くなる。

### B-8. Lightweight Charts の帰属表示要件

3.2節はライブラリを指定しているが、TradingView のライセンス条件には**帰属表示（ロゴ・リンク）の要件**が含まれる ★。個人利用でも条件は適用される。**採用した決定:** 画面下部に帰属表示リンクを常設し、ライセンス全文を同梱した。

### B-9. RPO 24時間の実質的な意味

4.4節は「RPO 24時間以内」とする。日次バックアップからは最大24時間分の足が失われるが、**1分足は Tiingo REST から再取得できる**。したがって実質的なデータ損失は「REST履歴が遡れる範囲を超えた分」および「ライブ集計にしか存在しない情報（`received_at`、進行中足）」に限られる。

**採用した決定:** リストア後に「最終保存足〜現在」を自動補完する手順を運用ドキュメントに含めた。RPOの実効値は24時間より大幅に良い。ただし補完はA-2のレート制限予算を消費するため、大規模復旧時は時間がかかる旨を明記した。

## 5. 軽微な指摘

| # | 箇所 | 指摘 |
|---|---|---|
| D-1 | 3.4節 | 「CSVまたはParquet」だが、Parquet出力には pyarrow が必要でメモリを数百MB使う。1GB機では**CSVのストリーミング出力を主とし、Parquetは任意依存**とすべき。実装では pyarrow 未導入時に 501 を返し、CSVは常時利用可能とした |
| D-2 | 4.3節 | 「過去1日分の1分足は数秒以内に表示」は、`(symbol, timestamp_utc)` の主キーがあれば数ミリ秒である。要件として緩すぎるが害はない |
| D-3 | 10.2節 | 1秒スナップショットの3案が併記されたままで、初期段階の決定が無い。実装では**保存しない（案1）**を既定とし、設定で保持日数を指定した場合のみ保存する形にした |
| D-4 | 11.2節 | 再接続バックオフに**ジッタ**の記述が無い。単一クライアントなので実害は小さいが、提供元側の障害復旧時に同時再接続を避けるため実装では乱数ジッタを入れた |
| D-5 | 13章フェーズ1 | 「楽天証券等の画面と価格を比較する」は自動化できない手動検証である。**判定基準（許容乖離幅）が無い**と結論が出ないため、運用ドキュメントにチェックリスト化した |
| D-6 | 3.1節 | 「データ提供元でサポートされない銘柄を明示できること」に対し、**未サポートを判定する手段**が定義されていない。実装では購読応答と履歴取得の結果から `symbols.supported` を更新する |
| D-7 | 6章の表 | Fly.io の月額「約4〜7米ドル」など各PaaSの単価は改定されうる ★。ただし6.1節が「削減額は数米ドル程度であり移行に見合わない」と正しく結論しているため、単価の誤差は判断を変えない |
| D-8 | 4.5節 | 「ログへAPIキー、Cookie、認証トークンを出力しない」に対し、**実施方法**が無い。実装ではログフィルタで既知の秘密情報パターンをマスクした |

## 6. 仕様書へ追記を推奨する項目

1. **A-1の判定基準**：フェーズ1に「30銘柄換算の月間転送量が無料枠の何%か」を実測し、超過時の意思決定（銘柄数削減／有料移行／主系変更）を分岐として明記する。
2. **A-2のレート予算設計**：REST呼び出しを「予算を持つ資源」として扱うことを非機能要件へ格上げする。
3. **A-3の単一Writer定義の修正**：11.1節を「時系列テーブルへの単一Writer」と限定する。
4. **A-4のアプリ層認証**：3.5節に「アプリ側で Access JWT を検証する」を追加する。
5. **B-1〜B-5のデータ規約**：10.1節に、時刻の基準（区間開始）、足の生成に使うイベント種別、提供元優先順位、`is_final` の上書き規則を明記する。
6. **10.4節に空き容量の前提**：整合バックアップ生成時にDBサイズと同等の一時領域が必要である旨。

## 7. 結論

仕様書は、**個人利用という制約下での技術選定としては質が高い**。特に、スケール・トゥ・ゼロを採用しない理由、複数APIの安易な併用を退けた理由、S3静的ホスティングを採用しない理由は、いずれも要件から正しく演繹されており、結論を支持する。

一方で、**自ら表に書いた無料枠の数値（1GB/月、REST 50回/時）を、自ら定めた規模（30銘柄）と突き合わせていない**点が最大の弱点である（A-1、A-2）。これは構成の選択ではなく実装の可否に関わるため、フェーズ1で最初に潰すべき項目である。

内部矛盾（A-3）と防御の欠落（A-4）、データ規約の未定義（B-1〜B-5）は、いずれも構成を変えずに解消できる。本リポジトリの実装は、上記の決定を採用した上で仕様書の構成に沿って構築している。
