コストと運用複雑性を最小化するため、メッセージブローカーやマネージドDBを 使わず、collector・API・Tunnelを1台に集約している。外部から開くポートは 管理用SSHだけで、Webは外向きCloudflare Tunnelを唯一の入口とする。

2. なぜこれで動くのか

この構成の非自明な点はひとつに集約される。1時間に50回しか外部を叩けないのに、 画面のチャートは数分おきに伸びていく。成立させているのは次の3つで、 どれか1つでも欠けると成り立たない。

Why 50 calls/hour is enough

実際の消費量（10銘柄・取引時間中）

鮮度を決めているのは USSTOCKS_FOREGROUND_POLL_SECONDS だけではない。 backfill_min_gap_seconds（既定120秒）が「その程度の隙間ならREST枠を使う価値がない」 として要求を捨てるため、前景の実効間隔は90秒設定でも約2分になる。 これは偶然ではあるが、下の表のとおり結果的に枠の中に収まっている。

用途設定実効間隔calls / hour
前景（表示中の1銘柄）foreground_poll_seconds=90約2分（min_gap 120秒に律速）約30
保険sweep（残り9銘柄）background_poll_seconds=36001時間9
再接続／起動時backfill都度—数回
銘柄検索catalogに無い語のみ—ほぼ0

履歴取得用の余白を確保

min_gap を下げて前景を本当に90秒間隔にすると40 calls/hourとなり、 保険sweepと合わせて49 calls/hourで、起動時backfillや検索を含める余地が ほぼなくなる。現在は通常時を約39 calls/hourに抑え、日足コーパス、 再接続backfill、検索のために約11 calls/hourの余白を確保している。

実線がいま流れている経路、破線が接続はするがデータの来ない経路である。 ブラウザの30秒更新はローカルDBの読み出しなので無料枠を消費せず、 同時に last_viewed_at を打ち直して「この銘柄をまだ見ている」ことを collectorへ伝え続ける。この打刻が止まると、5分後に前景から外れて 1時間間隔のsweepへ落ちる。

IEX単独フィードの被覆率

無料枠が見ているのはIEX（全米出来高の数%）だけである。実測では AAPLの通常取引で385/390本＝98.7%と実用範囲だが、 出来高の桁は統合気配より2〜3桁小さく、閑散銘柄や時間外では 足が飛び飛びになる。価格そのものは正確で、証券会社アプリとの差は 0.08%（MU 826.93 対 826.23、同一時刻）。 連続した足が要る場合はSIP（有料）へ移すしかない。

7. 再接続／欠損補完／ポーリング

collectorは同じBackfillCoordinatorを3つの用途で使う——起動時、 切断からの復帰時、そして定常のポーリングである。 入口が違うだけで、gap判定・要求合体・token取得は共通で、 どの経路から来ても無料枠を守る制御が1か所に集まる。

1要求の発生起動 / 銘柄追加 / 切断復帰 / poll loopの周期。
2gap判定最終足+1分からnowまでが120秒未満、または市場closedのみなら要求しない。
3要求合体同一symbolの範囲をwiden。lookback最大30日。
4token取得50/hourと1,000/dayをSQLiteへ永続化。
5確定bar保存REST結果をfinalとしてupsertしstate更新。

poll loopの判断順序

#判定やらない条件
115秒ごとに起床購読銘柄が0本
2has_open_window(now-2分, now)市場が閉じていれば何もしない——休場中に枠を消費しない
3recently_viewed(300秒)から前景銘柄を1つ選ぶ5分以内に誰も見ていなければ前景なし
4前景は90秒経過で対象、他は3600秒経過で対象まだ間隔に達していない
5request_gap_since_last_bar()gapが120秒未満（=前景の実効間隔が約2分になる理由）
6backfill loopが5秒後にdrain、tokenを1つ消費tokenが無ければ最大300秒待って再queue

再接続delayは1、2、4秒…最大60秒で、±25%のjitterを加える。接続が60秒以上 継続してから切れた場合はdelayを1秒へ戻す。REST枠が空なら最大300秒待ち、 取得できなければrequestをqueueへ戻す。providerが429を返した場合も 要求を捨てずに再queueし、300秒のcooldownを置く—— 捨てると、無関係な要因で同じ銘柄が再requeueされるまでgapが埋まらないままになる。 受信bytesも日／月windowへ永続化し、月間1GBの80%でwarningを出す （ストリームが無音の現在、この数値はほぼ増えない。実際 「月間受信 0.0 MB」がA-6を最初に示していた兆候だった）。

8. API／SSE／ブラウザ

初期画面はwatchlistと最新側の1年historyをRESTで1回取得し、同じ応答から 1D・7D・1M・1Yの4画面を描画する。その後は 30秒ごとの差分取得と、EventSourceによるsnapshot／status受信を 並行して回す。SSEは最大1時間で意図的にcycleし、ブラウザが自動再接続する。

初期表示

  1. /api/symbols?watched_only=true
  2. /api/bars/{symbol}?days=365を1回だけ取得
  3. 最新側の最大20,000 barsを、最新足を右端に1D・7D・1M・1Yへ分配して4分割描画
  4. 非取引日を含む暦日幅を不可視anchorで固定。履歴不足時だけ最古データを左端にする
  5. チャート選択時は同じ期間幅のまま単一画面へ拡大
  6. 「4分割」で高さ固定の2×2 overviewへ戻す
  7. /api/live?symbols=...へEventSource接続

継続更新

  1. 30秒ごとに/api/bars/{symbol}?start=最新足——ローカルDB読み出しなのでREST枠を消費しない
  2. 同じ要求がlast_viewed_atを打刻し、collectorの前景ポーリングを維持する
  3. タブが非表示の間は停止し、復帰時に即座に1回実行
  4. SSEはlive.db由来のupdate／status／15秒heartbeat（ストリーム休止中はstatusとheartbeatのみ）
  5. SSE error時は/api/pingで認証失効を区別
なぜ30秒か

この要求はSQLiteの読み出しであってproviderへは届かないため、頻度は無料枠ではなく 「確定した1分足をどれだけ早く見せたいか」だけで決まる。同時に、これが viewer_idle_seconds=300を満たし続ける唯一の仕組みでもある—— 打刻が止まれば5分後に前景から外れ、1時間間隔のsweepへ落ちる。

9. データベースと所有権

「単一writer」は時系列テーブルに限定される。APIはwatchlist編集のため symbolsへ短時間writeする。WAL、5秒busy timeout、thread-local connectionにより複数readerと設定writeを共存させる。 symbols.last_viewed_atもAPIが書き、collectorが読む—— 両プロセス間に新しいIPCを足さずに済ませるため、既に数秒ごとに読まれている このテーブルへ相乗りしている。

catalog importが書込ロックを長く握らない理由

symbol_catalogは約10万行を扱う。1トランザクションで書くと、 その間にcollectorのbar書込がbusy timeout（5秒）を使い切ってしまうため、 2,000行ずつのチャンクに分けて書き込む。整合性は行ごとのrefreshed_at スタンプで担保し、取り込み完了後に「今回のスタンプ以外」を削除する。 スタンプにはマイクロ秒とUUIDを含める——秒精度では、同じ秒に2回走ったとき 古い行が消えずに残った。

10. CI/CD

AWS desired stateとアプリrolloutは別経路で進む。GitHub ActionsはTerraformを applyし、アプリはLightsailがprivate repositoryをpullする。

Lane A — GitHub Actions

  1. infra/**を含むmain push / PR / manual dispatch
  2. Python 3.11、install、ruff、pytest
  3. Terraform fmt、backendなしinit、validate
  4. main pushのみOIDCでdeploy roleをassume
  5. S3 state lock → plan → apply → outputs

Lane B — Host pull deploy

  1. systemd timerが2分ごとに起動
  2. read-only keyでorigin/main fetch
  3. 変更なし／local dirtyなら停止
  4. revision別venv作成 → current symlinkを原子的切替
  5. collector/API restart → /api/livez確認
  6. 失敗時は前releaseへ自動rollback
実効上、Lane BはLane Aの成功を待たない

deploy agentはGitHub workflow statusを確認しない。テスト中またはテスト失敗の commitでも、mainに存在すればアプリへ反映し得る。CI成功でCDを gateするには、成功済みSHA／release tag／deployment markerが必要。

OIDC trustはrepositoryとrefs/heads/mainへ固定され、PR tokenは roleをassumeできない。長期AWS access keyをGitHubへ保存しない。pull方式は GitHub-hosted runnerの送信元IPが固定されない問題を避け、Lightsail SSHを 0.0.0.0/0へ開かずに済ませる。Lane BはGitHub Actionsを実行せず、 Actions quotaやartifact容量を消費しない。アプリコードだけのmain pushは workflowのpaths filterによりLane A自体を起動しない。

13. 現行実装で確認した注意点

以下は設計上の一般論ではなく、コードとデプロイ構成を突き合わせた結果。 本番運用前の優先確認事項となる。

沈黙はWSとRESTを分ける

collectorは自分が処理するmessageType（A／E） しか記録しない。購読確認Iとheartbeat Hは痕跡なく捨てられるため、 WSだけでは「接続はしているがデータが来ない」を判定できない。 現在の生存経路であるRESTは3回連続空fetchでsymbol警告を出し、 有効barの復帰時に自動解除する。既知の配信終了後は16:45 ETでpoll自体を止める。

履歴取得用の余白を確保

前景+保険sweepは通常約39 calls/hour（上限50）。残りを日足コーパス、 起動時backfill、検索へ回せる。前景を実効90秒へ縮めると通常分だけで 49 calls/hourになるため、healthのrest_calls_hourは継続監視する。

健全性の判定が実態とずれる

/api/healthはWebSocketが繋がっていればconnectedとみなす。 いまはデータが来なくても繋がるため、この項目は生存を意味しない。 実際の鮮度は最新barのtimestampで見る。

CIとCDの独立性

pull agentはworkflow成功を待たないため、mainへ入ったcommitをテスト完了前に deployできる。Actions quota中は特にlocal testが必要。

手動bootstrap境界

secret deploy keyをuser_dataへ埋めないため、最初のprivate repo cloneと installer実行はout-of-bandで行う。

atomic release + rollback

完成済みvenvへsymlinkを切り替え、health失敗時は前releaseへ戻す。 失敗SHAの2分ごとの再試行も抑止する。

unit変更はinstaller再実行

Python／webの変更はpull agentだけで反映されるが、 deploy/systemd/*.serviceやtimerを変えた場合は install.shの再実行が要る（catalog timerの追加時がこれに当たった）。

通知の空白

CPU burstとcost以外のapp-level異常はSNSへ未配線。journalと /api/healthのhost側監視が次の改善点。

ComposeからのDB handoff

named volumeのmarket.dbを一度だけ整合コピーし、collectorを二重起動しない。 installerは移行漏れを検出して停止する。

14. 日足＋ニュース分析コーパス

常駐負荷と部分uploadを増やさない

Phase 3は毎日13:30 JSTのoneshot。DuckDBは1 thread・256MB、 systemdは512MB上限で、ローカルParquetだけを読む。 出力はevent明細・集計・未接続tickerのParquetとJSON／Markdown／HTML。 APIは軽量JSONだけを読み、DuckDB／pyarrowをimportしない。 S3では世代ごとのmanifest.jsonを最後に更新し、同一digestは再送しない。

ニュース本文はNotionではなくS3を再処理可能な正本にする

要約だけでも価格反応日は計算できるが、将来の再分類と要因検証には取得時の 情報量が必要になる。Notionは見出し・500字要約・見立て・URL・content hashを持つ 人向け索引、S3のcorpus/articles/は許諾範囲内のgzip本文snapshot、 news Parquetは企業・製品・数量・供給関係・根拠spanを持つ分析用索引とする。 sentimentは属性の1つに留める。paywall、認証、robotsを回避せず、保存できない媒体は RSS本文・要約・URL・hash・失敗理由だけを残す。

Notion APIは平均3 request/秒、1 request 500KB／1,000 blocks、rich text object 2,000文字。Freeの1人workspaceと有料planはblocks無制限だが、Freeでownerが2人以上 なら通算1,000 blocksで削除しても枠は戻らない。容量よりも再抽出・重複排除・移行の しやすさを理由に、全文正本をNotionから分離する。

本番初回結果（2026-07-31）

Notion 368ページからticker付き17イベントを展開し、段階導入中の日足corpusへ 1件を接続、16件を未接続Parquetへ記録した。初回は6ファイルをS3へ送り、 同一入力の再実行は0 upload。CPU時間は約1.3秒で、timerはactive。
